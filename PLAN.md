# KptnCook favorites to Tandoor sync service

## Goal and decisions

Create a separate Python service alongside `kptncook/`, deployed with Docker Compose. Use the latest published stable KptnCook release as a dependency, pulled from PyPI during each service-image build; do not modify, fork, or copy its code. It imports current KptnCook favorites into Tandoor once, runs on startup and every 24 hours thereafter, and never modifies or recreates a successfully imported recipe, even if it is later removed from Tandoor. Removing a favorite does not delete anything. Start with empty history: existing Tandoor imports are not adopted and can be duplicated on the first run. There is no manual sync trigger requirement.

Target the latest Tandoor release; 2.7.2 is the initial compatibility target supplied by the user. Recheck the latest release and API compatibility when implementing and upgrading, rather than assuming a moving version remains compatible.

## Current state

- `kptncook/src/kptncook/api.py` already authenticates with an access token, lists favorites and resolves their OID/UID identifiers to full recipes. The mobile API is unofficial and its payload and completeness/pagination guarantees need verification.
- `kptncook/src/kptncook/tandoor.py` converts recipes to Tandoor **ZIP import** data, including source URL, servings, keywords, steps, ingredients and optional cover. This is not a verified REST create payload: notably, the export places an ingredients list at the top level, while Tandoor 2.7.2's `RecipeSerializer` requires steps containing nested ingredients. Adapt and verify the conversion rather than POSTing the ZIP payload unchanged.
- The existing Dockerfile already installs the published package. The separate service will explicitly use the latest stable PyPI release rather than the checkout; PyPI reports 0.0.39 at planning time. The checkout illustrates available integration points, but the installed release must be checked for those interfaces during implementation.
- Tandoor 2.7.2's `cookbook/views/api.py` and `cookbook/serializer.py` expose a recipe model create endpoint and a separate multipart image action. The API settings describe Bearer tokens with scopes. Confirm exact routes, fields, accepted values, and permissions with the running target instance's API schema and integration tests.

## Implementation todos

1. **Create service skeleton and source integration.** Add a standalone service directory and dependency/build configuration. Install the latest stable published `kptncook` package from PyPI at image build time and reuse its client, recipe models and conversion helpers without changing its code. Prefer public interfaces; isolate any necessary private-interface usage behind a service adapter. Configure the build to invalidate or bypass the relevant Docker and package cache when selecting the release, so a rebuild actually checks for a newer stable version; document the exact rebuild command. Record the resolved package version in image metadata/logs. Keep service dependencies controlled and run compatibility checks against the resolved release; a future upstream change can break a build or integration and must not silently corrupt sync behavior. Define config for KptnCook API key, access token, language/store, Tandoor base URL and token, schedule interval, and persistent state path.
2. **Implement favorites acquisition and normalization.** Fetch the current favorites directly, treating a verified empty list as a successful no-op. Resolve identifiers to full validated recipes and use each full recipe's nonempty canonical OID as the durable identity; map UID summaries to that OID, deduplicate aliases, and report unresolvable/partial entries. Never turn malformed, failed, or incomplete responses into a successful empty inventory. Verify actual source pagination/limits and safely handle them; if completeness cannot be established, surface the limitation rather than silently dropping favorites. New favorites remain eligible in later runs.
3. **Implement Tandoor API adapter.** Use scoped Bearer credentials and the actual instance schema to create recipes and upload covers. Adapt existing converter output into the nested API structure, preserving title, description, source URL, servings, time, keywords, ingredient groups, amounts, units, and instructions without double-counting ingredients. Verify empty/null fields, ordering and translations. Reuse the existing safe image download logic and send bytes as multipart; do not forward KptnCook secrets or credential-bearing URLs to Tandoor. An unavailable or failed image is logged and skipped permanently; never recreate or change the recipe to retry it.
4. **Build durable import history and crash-safe state machine.** Use SQLite on a persistent local volume with a schema/version and binding to one source account and destination URL/space identity, so accidental configuration changes cannot silently reuse the wrong history. Before each create, commit an `in_flight` record for the canonical source OID; after a validated success response commit the Tandoor ID and `imported` status immediately, before attempting an image. An imported record is a permanent tombstone even if Tandoor later returns 404, the source favorite disappears, or the container restarts. Serialize runs with a process-level lock covering the entire sync; document a single instance and a filesystem supporting the chosen lock and SQLite durability. Do not automatically retry creates when a request or process may have reached Tandoor, including crash after POST, lost response, malformed success, or server error of uncertain side effects. Keep these records blocked as `uncertain`, report them, and process other independent recipes. Retry only failures proven to precede any remote write.
5. **Provide explicit reconciliation and operational visibility.** Add non-scheduling administrative CLI commands to list uncertain records and resolve each after a human inspects Tandoor: mark imported with a verified destination ID, or explicitly clear for retry after confirming no recipe was created. Never infer absence solely from a search result or matching title. Validate command input, bind changes to the same locked state, and document the duplicate risk. Log run summaries and actionable per-recipe failures without secrets or recipe bodies; clearly distinguish auth failures, malformed source data, Tandoor errors, uncertain writes and image warnings.
6. **Package and document deployment.** Compose runs one non-root container with a persistent writable volume, environment/secrets supplied outside source control, bounded HTTP timeouts, graceful shutdown, and restart behavior; execute once on startup, then wait 24 hours after each completed run (configurable interval, no overlapping runs). Document token acquisition/scopes, source API key and account token, base URL/space, HTTPS, startup, logs, volume permissions, backup/restore of SQLite consistently with Tandoor, initial duplication, recovery, resetting history, upgrades and the consequences of lost/stale state. Document unofficial API and personal-use/terms considerations.
7. **Verify behavior and compatibility.** Unit tests for source shapes, empty/invalid/partial responses, ID aliasing, payload fidelity and API validation; mocked HTTP/state tests for successful import, unchanged rerun, deletion, unfavorite/refavorite, restart, duplicate favorites, partial failures, auth failures, overlapping runs, failed image, persistence failure, timeout and crash at every write boundary, reconciliation, and destination mismatch. Test that the service image build resolves the current stable KptnCook release even on rebuild, checks its required interfaces, and runs Compose with a mounted volume. Run an opt-in end-to-end test against a disposable supported Tandoor instance using representative source fixtures, confirming actual nested ingredients, images, token scopes and deletion semantics; never alter a real user's library during automated tests. Run applicable formatting, lint, type checking and test commands.

## Safety and limitations

- Local durable history, not Tandoor inventory, is the source of truth for successful imports. Losing or rolling back the volume can cause duplicates or reimports; back it up and restore it coherently. Existing imports are intentionally not discovered.
- Exactly-once creation cannot be guaranteed across independent HTTP and SQLite transactions without a server-side idempotency guarantee. The durable pre-write marker plus manual reconciliation favors avoiding duplicates over automatic recovery; even a crash just before sending may require manual resolution.
- Secrets are runtime configuration only; redact URLs and errors, restrict token scopes and file permissions, and avoid sending the KptnCook API key on redirects to untrusted hosts. Never delete or overwrite Tandoor content automatically.
- Pulling the latest stable KptnCook release on every build intentionally sacrifices reproducible builds and may introduce upstream breaking changes; record the resolved version, test each image, and retain a previously working image for rollback. Already-built images do not update until rebuilt and redeployed.
- Version 2.7.2 source confirms the serializer/view structure but does not prove deployment-specific compatibility; test the target version's live schema and behavior. Upstream Tandoor and unofficial KptnCook APIs can change.
